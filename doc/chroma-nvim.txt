1. INTRODUCTION                                      *chroma-nvim-introduction*

Chroma Neovim is a Neovim configuration for people who work with Terraform,
Terragrunt, Kubernetes, Helm, Ansible, Docker and YAML, and who live inside a
terminal rather than an IDE.

It is not a general-purpose configuration with DevOps features bolted on.
DevOps is the starting point, and choices are made accordingly: two-space
indentation everywhere because a tab is a YAML parse error, schema validation
for Kubernetes manifests, a Helm language server that actually attaches.

The intended workflow is:
>
    Kitty -> Zellij -> Yazi -> Neovim
<
That last hop matters more than it looks. Zellij intercepts several control
keys before Neovim sees them, and this configuration is built around that
fact — see |chroma-nvim-zellij|.

==============================================================================
2. REQUIREMENTS                                      *chroma-nvim-requirements*

Hard requirements ~

  Neovim >= 0.12      This configuration uses the native LSP API
                      (|vim.lsp.config|, |vim.lsp.enable|) and the rewritten
                      nvim-treesitter, neither of which exists earlier.
  git >= 2.19         Partial clones, required by lazy.nvim.
  curl, tar           Parser and binary downloads.
  A C compiler        Treesitter parser compilation.
  tree-sitter-cli     >= 0.26.1, installed from your system package manager.
                      The npm build is explicitly not supported upstream.

Strongly recommended ~

  ripgrep (rg)        Backend for grep pickers.
  fd                  Required by project.nvim for session handling.
  fzf >= 0.36         Backend for every picker.
  A Nerd Font         Icons in pickers, file trees and completion.
  lazygit, yazi       Git UI and file manager integration.

External tools, as needed ~

  terraform or tofu, terragrunt, kubectl, helm, ansible, aws, docker

These belong to your system. Chroma does not install, upgrade or replace any of
them, and enabling a component does not ask for one: choosing Kubernetes asks
for Chroma's Kubernetes features, not for kubectl. A missing one never blocks an
installation. `chroma install` names what is not on PATH when it finishes,
`:checkhealth chroma` and `chroma doctor` name it again whenever you ask, and
the feature that needs it says so when you use it.

Language servers and linters are a different matter: those are Chroma's own
runtime, they are installed automatically by Mason, they are pinned so that one
release installs the same editor twice, and they do not need to be present
beforehand.

3. INSTALLATION                                      *chroma-nvim-installation*

This repository IS a Neovim configuration directory. It does not install into
one — it becomes one.

Try it first, without touching your setup ~

|$NVIM_APPNAME| lets Neovim use a different configuration directory, so this
can run beside whatever you already have. Nothing is overwritten and nothing
is shared: plugins, sessions and Mason packages all live under the new name.
>
    git clone https://github.com/ultherego/chroma-nvim.git \
        ~/.config/chroma-nvim

    NVIM_APPNAME=chroma-nvim nvim
<
Keep it by aliasing that, in your shell's own config file: >

    # bash / zsh
    alias dvim='NVIM_APPNAME=chroma-nvim nvim'

    # fish
    alias --save dvim 'NVIM_APPNAME=chroma-nvim nvim'
<
Adopt it as your main configuration ~

Only once you have decided. Move any existing configuration aside first —
`ln -s` will not replace a directory, and you will want the old one back if
you change your mind: >

    [ -e ~/.config/nvim ] && mv ~/.config/nvim ~/.config/nvim.backup

    git clone https://github.com/ultherego/chroma-nvim.git ~/.config/nvim
    nvim
<
If you would rather keep the clone with your other projects and link it — so
that `git status` in it behaves like any other repository — that works too: >

    git clone https://github.com/ultherego/chroma-nvim.git ~/src/chroma-nvim
    mkdir -p ~/.config
    ln -s ~/src/chroma-nvim ~/.config/nvim
<
Nothing in the configuration depends on where the clone lives.

The first start ~

lazy.nvim bootstraps itself, installs every plugin, and Mason fetches the
language servers and tools while treesitter compiles its parsers. Give it a
minute. Then: >

    :checkhealth chroma   external tools this config expects, and what stops
                          working without each one
    :Lazy                 plugin status
    :Mason                language server and tool status
    :checkhealth          everything at once
<
`:checkhealth chroma` is the one to read first. Most of this configuration
drives external programs, and when one is missing the symptom is usually
silence rather than an error.

Going back ~

Nothing is installed outside these directories: >

    ~/.config/nvim          or ~/.config/<appname>
    ~/.local/share/nvim     plugins, Mason packages, treesitter parsers
    ~/.local/state/nvim     undo history, sessions, logs
<
Removing those, and restoring any backup you moved aside, leaves no trace.

4. LAYOUT                                                  *chroma-nvim-layout*
>
    init.lua                    entry point; leader keys, then the layers
    lua/config/
      options.lua               editor options
      keymaps.lua               keymaps that need no plugin
      commands.lua              commands that need no plugin
      parsers.lua               which treesitter parsers are installed
      lazy.lua                  plugin manager bootstrap
    lua/plugins/
      <domain>.lua              one file per domain, one domain per file
    lua/chroma-vault/           our own plugin  :help chroma-nvim-vault
    lua/chroma-terraform/       our own runner  :help chroma-nvim-terraform
    lua/chroma-aws/             our own module  :help chroma-nvim-aws
    lua/chroma/                 this configuration talking about itself
      components.lua            which components exist, and which are on
      tasks/                    the execution layer  :help chroma-nvim-tasks
      health.lua                :checkhealth chroma
    after/lsp/
      <server>.lua              per-server LSP overrides
    components/                 the component contract, read here and by
                                the CLI that installed this
    doc/                        this file, and the documents beside it
    lazy-lock.json              the plugin versions this release was tested
                                against
    README.md, LICENSE          so the installed directory says what it is
      assets/                   and the image the README shows
<
That is an installation, which is deliberately not a checkout: the installer,
the test suite and the lint configuration are not copied in, and neither is
`.git` — an installed configuration that is also a repository invites a
`git pull` on top of a managed installation, and that arrives at a version no
install state describes.

Two of the documents in `doc/` govern the rest. `CONTRACT.md` is what this
configuration promises, including the whole repository tree; `DECISIONS.md` is
why each part of it is the way it is, and what is deliberately absent.
`KEYMAPS.md` is every mapping on one page, for reading outside the editor.

The split is deliberate. Anything that belongs to a plugin — its keymaps, its
options — is defined in that plugin's spec, not in a central keymap file. If
you remove the plugin, its keys leave with it.

Our own modules are directories rather than files in one shared namespace, and
each depends on nothing else here, so any of them can be lifted into its own
repository without edits. `lua/chroma/` is the opposite category: not a tool,
but the configuration's account of itself.

`after/lsp/` is not decoration; it is how Neovim 0.12 layers LSP settings.
See |chroma-nvim-lsp|.

5. KEYMAPS                                                *chroma-nvim-keymaps*

The leader key is <Space>. Every prefix is assigned exactly once, globally,
and declared in one place (which-key's spec in `lua/plugins/ui.lua`) so that a
collision shows up as a visible duplicate instead of a mapping that silently
stops working.

Press <Space> and wait: which-key lists what is available. `<leader>?` lists
buffer-local mappings only.

Groups ~
>
    <leader>f    Find            <leader>b    Buffers
    <leader>p    Project         <leader>w    Windows
    <leader>g    Git             <leader>s    Sessions
    <leader>l    LSP             <leader>x    Tools
    <leader>t    Terraform       <leader>k    Kubernetes
    <leader>a    Ansible         <leader>A    AWS
<
The last four appear only when the component that defines the keys under them
is enabled, so which-key describes the editor you have. `<leader>a` follows
`vault` rather than `ansible`: every key under it is an Ansible Vault key, and
the two components are independent of each other.

Find ~
>
    <leader>ff   Files                    <leader>fh   Help tags
    <leader>fg   Grep                     <leader>fk   Keymaps
    <leader>fw   Word under cursor        <leader>fd   Diagnostics
    <leader>fb   Buffers                  <leader>fr   Resume last picker
    <leader>fo   Recent files
    <leader>fp   Find path — type it, Tab completes
    <leader>fe   File explorer (oil)
    <leader>fy   Yazi at current file
    <leader>fY   Yazi at working directory
    <leader>ft   Resume last yazi session
<
`<leader>ff` and `<leader>fp` answer different questions. The first is the
fuzzy finder, for when the name is roughly remembered and the location is not.
The second leaves `:FindFile ` on the command line for a path you already know,
where Tab completes directory by directory the way it does anywhere else in
Neovim. Neither replaces the other and `<leader>ff` is unchanged.

Project ~
>
    <leader>pp   Projects
<
Terraform ~
>
    <leader>ti   Init          <leader>tp   Plan
    <leader>tv   Validate      <leader>ta   Apply the reviewed plan
    <leader>td   Discard the reviewed plan
<
`:TerraformPlanDestroy` has no mapping on purpose — see |chroma-nvim-terraform|.

AWS ~
>
    <leader>Ap   Pick profile      <leader>As   Show profile and region
    <leader>Ar   Pick region       <leader>Aw   Who am I (sts get-caller-identity)
    <leader>Ac   Restore the starting environment
<
Sessions ~
>
    <leader>ss   Select a session      <leader>sw   Save now
    <leader>sl   Load for this dir     <leader>st   Toggle recording
    <leader>sL   Load the last one     <leader>sd   Delete this session
<
Kubernetes ~
>
    <leader>kk   Open the cluster view
    <leader>kt   Open it in a new tab
    <leader>kx   Switch context
    <leader>kn   Switch namespace
<
Inside a cluster view, navigation is hierarchical — deployment, pod,
container — with `<CR>` to descend and `<BS>` to go back. `gd` describes,
`gl` shows logs, `gS` opens a shell, `gy` shows YAML, `ge` edits, `gD`
deletes, `gP` lists port-forwards, and `1`-`6` jump straight to deployments,
pods, configmaps, secrets, services and ingresses.

Three of the plugin's defaults are remapped because Zellij eats them: >

    picker            <C-p>  ->  <C-e>
    namespace view    <C-n>  ->  gn
    toggle headers    <M-h>  ->  gH
<
Ansible ~
>
    <leader>ar   Plan and run an Ansible playbook
    <leader>aR   Repeat the last Ansible invocation
    <leader>av   Reveal the encrypted value under the cursor
    <leader>av   Encrypt the selection in place        (visual mode)
    <leader>aV   Show where the vault password comes from
<
`<leader>ar` asks for the playbook, the working directory, the inventory, the
tags, a limit and the CLI overrides, then shows the exact argument vector and
asks once before anything runs. It infers nothing from the buffer: the buffer
is offered as one row in a picker. Ansible itself is not started until a
separate question naming the directory, the playbook and the inventory has been
answered yes. `<leader>aR` goes straight to that final preview with the last
invocation's decisions, and still asks. Both are also `:AnsibleRun` and
`:AnsibleRepeat`.

Vault handling is chroma-vault.nvim, written for this project — see
|chroma-nvim-vault|.

Playbooks, roles, `group_vars`, `host_vars`, `defaults`, `tasks`, `handlers`
and `molecule` files are detected as `yaml.ansible`. That filetype is what
activates ansible-lint and the ansiblels language server, and it also points
`K` at `ansible-doc`.

LSP ~
>
    <leader>li   LSP status (:checkhealth vim.lsp)
    <leader>ls   Document symbols
    <leader>lS   Workspace symbols
    <leader>ld   Document diagnostics
    <leader>lo   Outline (aerial)
    <leader>lt   References and definitions in a panel (trouble)
    <leader>lm   Mason
<
Inside a buffer with the outline attached, `[s` and `]s` jump between
symbols. Upstream's example uses `{` and `}`, which are Neovim's paragraph
motions — taking those would remove a core movement from every source buffer.

Rename, code action, references, implementation and type definition are
Neovim built-ins and are not duplicated — see |chroma-nvim-builtin-keys|.

Buffers and windows ~
>
    <leader>bd   Delete buffer            <leader>ws   Split horizontally
    <leader>bD   Delete buffer (force)    <leader>wv   Split vertically
    <leader>bb   Previous buffer          <leader>wc   Close window
                                          <leader>wo   Close other windows

Git ~

lazygit runs inside Neovim, themed from the active colourscheme: >

    <leader>gg   Lazygit

    <leader>gf   Lazygit file history
    <leader>gc   Search commits by message
    <leader>gC   Search commits touching this buffer

Hunk operations, buffer-local wherever gitsigns is attached: >

    ]h  [h       Next / previous hunk
    <leader>gs   Stage hunk, or unstage it if already staged
    <leader>gr   Reset hunk
    <leader>gS   Stage buffer          <leader>gR   Reset buffer

    <leader>gd   Diff against index
    ih           Hunk text object — `dih`, `vih`

`<leader>gs` and `<leader>gr` also work on a visual selection, staging or

In a diff split, `]h` and `[h` defer to Neovim's own `]c` and `[c`.

Tools ~
>
    <leader>xr   Run a task this project declares
    <leader>xs   Shell — a terminal at the bottom, toggled
    <leader>xf   Format buffer or selection   (also works in visual mode)
    <leader>xF   Toggle format on save
    <leader>xi   Formatter info (:ConformInfo)
    <leader>xl   Lint buffer now
    <leader>xt   Todo comments
    <leader>xT   Todo comments to quickfix
    <leader>xx   Diagnostics, whole workspace  (trouble)

    <leader>xq   Quickfix list                 (trouble)
    <leader>xL   Location list                 (trouble)

`<leader>xr` runs what the repository declares in `.chroma/tasks.json`, and

Editing ~

Surrounding pairs, on `gs` rather than the upstream `s`: >

    gsa   Add surrounding      — gsaiw" wraps a word in quotes
    gsd   Delete surrounding   — gsd" removes them again
    gsr   Replace surrounding  — gsr"' swaps quotes
    gsf   Find surrounding to the right      gsF   to the left
    gsh   Highlight surrounding
<
mini.surround's own default prefix is `s`, which shadows Neovim's built-in
`s` in normal and visual mode. Since `s` is a perfectly good key, the prefix
moved to `gs` — Vim's `gs` only means "sleep", which nobody misses.

Extra text objects, from mini.ai: >

    f    Function call      cif   changes what is inside call(...)
    a    Argument           cia   changes one argument
    t    Tag
    (  [  {  "  '          brackets and quotes, with whitespace variants
<
Each accepts next/last variants: `cin"` acts on the next quoted string, `cil"`
on the previous one.

TODO, FIXME, HACK, WARN, PERF, NOTE and TEST comments are highlighted, and
`<leader>xt` lists them all.


Editing, visual mode ~
>
    <leader>p    Paste without overwriting the register
    J / K        Move the selection down / up, reindenting
    < / >        Shift, keeping the selection
<
Outside the leader ~
>
    -            Open the parent directory in oil
<
Inside an oil buffer ~
>
    <CR>         Open                     g.           Toggle hidden files
    -            Parent directory         gs           Change sort order
    _            Open working directory   gx           Open externally
    <C-v>        Open in vertical split   g\           Toggle trash
    <C-x>        Open in horizontal split g?           Help

Note that oil's upstream defaults for splitting and previewing are <C-s>,

Groups not yet populated ~

AWS and Sessions are declared but still empty. The prefixes are
reserved so that later layers cannot collide with what already exists.

First run of the cluster view                       *chroma-nvim-kubectl-first*

kubectl.nvim uses a prebuilt Rust binary, downloaded on first use rather than
at install time. The first `<leader>kk` therefore reports
>
    [Kubectl.nvim] Downloading binary; restart Neovim to apply.
<
and does nothing else. Restart Neovim once and it works from then on. This is
expected, not a fault.

It also needs a working kubeconfig — without one there is no cluster to show.

A note on gitsigns                                  *chroma-nvim-git-api*

The gitsigns keymap block reproduced in most guides calls functions upstream
has since deprecated:
>
    next_hunk() / prev_hunk()   ->  nav_hunk('next') / nav_hunk('prev')
    undo_stage_hunk()           ->  stage_hunk() on a staged sign; it toggles
    toggle_deleted()            ->  preview_hunk_inline()
<
This configuration uses the current API. If you copy a mapping in from
elsewhere, check it against `:help gitsigns` first.

7. ZELLIJ INTEROPERABILITY                                 *chroma-nvim-zellij*

This is the part of the configuration that will confuse anyone reading it
without context.

If you do not use Zellij, skip this section — the remappings it describes are
harmless, and the upstream keys they replace mostly keep working alongside
them. Nothing here needs undoing.

The problem ~

Zellij's default keybindings put mode switches on plain control keys inside a
`shared_except "locked"` block, which means they are intercepted in every mode
— including while you are typing into Neovim. A stock configuration takes:
>
    Ctrl-g   lock mode          Ctrl-s   scroll mode
    Ctrl-q   quit               Ctrl-t   tab mode
    Ctrl-h   move mode          Ctrl-p   pane mode
    Ctrl-o   session mode       Ctrl-n   resize mode
    Ctrl-b   tmux mode
<
Alt is largely taken too: Alt-h/j/k/l move focus, Alt-f toggles floating
panes, Alt-i/o move tabs, Alt-n opens a pane.

Check yours rather than trusting the list: >

    rg 'bind "Ctrl' ~/.config/zellij/config.kdl
<
With no config.kdl, Zellij is on its defaults and the list above applies.

What it costs ~

Several Neovim built-ins become unreachable while Zellij is unlocked: Ctrl-h
as backspace in insert mode, Ctrl-o for the jumplist, Ctrl-b for page up,
Ctrl-t for the tag stack. No editor configuration can recover them — the key
never arrives.

Three ways out, in increasing order of effort:

  - Press Ctrl-g to lock Zellij while you need them, and again to unlock.
  - Move Zellij's mode switches onto a prefix Neovim does not use.
  - Accept it. The keys this configuration defines all avoid them anyway.

What this configuration does ~

No keymap defined here uses a captured key, and plugin defaults that landed on
one were remapped rather than left silently dead:
>
    oil        <C-s> <C-h> <C-t> <C-p>  ->  <C-v> <C-x> gp
    fzf-lua    ctrl-s                   ->  ctrl-x
               alt-h alt-i alt-f        ->  alt-. alt-, alt-/
    blink.cmp  <C-n> <C-p> <C-b>        ->  <C-j> <C-k> <C-u>/<C-d>
<
Without this, four oil mappings, four in fzf-lua and three in blink — including
next and previous completion item — would do nothing at all, with no error to
explain why.

`:checkhealth chroma` reports whether you are inside Zellij.

8. LSP                                                        *chroma-nvim-lsp*

Neovim 0.12 configures language servers natively. The pattern found in most
older guides is deprecated and will eventually error: >

    require('lspconfig').terraformls.setup{}    " do not do this
<
nvim-lspconfig no longer configures anything. It ships `lsp/<name>.lua` files
that Neovim discovers by itself; configuration happens through
|vim.lsp.config| and |vim.lsp.enable|.

Settings resolve in this order, each merging over the previous
(see |lsp-config-merge|):
>
    1. vim.lsp.config('*', ...)                lowest
    2. lsp/<name>.lua       on 'runtimepath'   from nvim-lspconfig
    3. after/lsp/<name>.lua on 'runtimepath'   yours
    4. vim.lsp.config('<name>', ...)           highest
<
So to change one setting of one server, add just that setting to
`after/lsp/<server>.lua`. Everything upstream provides stays in place. For
example `after/lsp/yamlls.lua` adds schemas while the upstream file's
formatting and telemetry settings survive untouched.

Servers installed ~

terraformls, helm_ls, dockerls, docker_compose_language_service, yamlls,
ansiblels, bashls, jsonls, lua_ls.

Helm                                                  *chroma-nvim-lsp-helm*

Neovim does not detect the `helm` filetype on its own; a template next to
`Chart.yaml` is seen as plain YAML. `helm_ls` only attaches to `helm` and
`yaml.helm-values`, so without filetype detection it would never start, and
`yamlls` would try to parse Go templates as YAML and fill the file with
errors. The `vim-helm` plugin provides the detection.

Tools that are also servers                          *chroma-nvim-lsp-dual*

`stylua` and `tflint` both ship an LSP mode, and nvim-lspconfig exposes
configs for them. Installing either as a tool therefore also starts it as a
language server.

  stylua   excluded from `automatic_enable`, because formatting belongs to
           conform.nvim.
  tflint   kept as a server, so Terraform diagnostics arrive over LSP. The
           lint layer must not register it with nvim-lint as well, or every
           finding would be reported twice.

9. TREESITTER                                          *chroma-nvim-treesitter*

nvim-treesitter maintains two incompatible branches. `master` targets Neovim
0.11; `main` is a full rewrite and is what Neovim 0.12 should use. This
configuration is on `main`, which means the familiar call
>
    require('nvim-treesitter.configs').setup({ highlight = { enable = true } })
<
does not apply — that module does not exist. Parsers are installed with
`require('nvim-treesitter').install()` and highlighting starts per buffer via
|vim.treesitter.start()|.

Highlighting and folding are enabled for every filetype that has a parser.
Indentation is deliberately left to Neovim's own indent scripts, which are
mature for yaml, terraform, hcl, json, lua, bash, python and go.

Commands: `:TSInstall`, `:TSUpdate`, `:TSUninstall`, `:TSLog`.

10. COMPLETION                                         *chroma-nvim-completion*

blink.cmp, pinned to the v1 release line, which ships prebuilt Rust binaries
so no cargo toolchain is needed.

Inside the completion menu ~
>
    <C-space>    Show menu / toggle documentation
    <C-j>        Next item              <C-k>   Previous item
    <Down>       Next item              <Up>    Previous item
    <C-y>        Accept                 <C-e>   Cancel
    <C-d>        Scroll documentation down
    <C-u>        Scroll documentation up
    <C-l>        Toggle signature help
    <Tab>        Snippet forward        <S-Tab> Snippet backward
<
Sources: LSP, paths, snippets, buffer. Snippets come from friendly-snippets.

blink is loaded eagerly rather than on |InsertEnter|. It registers its
completion capabilities through |vim.lsp.config|, so it has to be in place
before the first language server attaches — otherwise servers start with the
plain built-in capabilities and completion quietly degrades.

11. FORMATTING                                         *chroma-nvim-formatting*

conform.nvim formats on save, and `<leader>xf` formats on demand.

Formatters by filetype ~
>
    lua                 stylua
    terraform           terraform_fmt, or tofu_fmt where only tofu is installed
    hcl                 terragrunt_hclfmt
    sh, bash            shfmt
    json                jq
    yaml, dockerfile    the language server
<
Anything without an entry falls through to the language server, because
`lsp_format` is set to "fallback". Verified by reading
`documentFormattingProvider` off the attached client: yamlls and dockerls both
report `true`, so YAML and Dockerfiles really are covered. helm_ls reports
`nil` — Helm templates are formatted by nothing, and a YAML formatter could
not safely handle Go templates interleaved with YAML anyway.

Adding an opinionated YAML formatter on top of yamlls would only create noise
in Kubernetes diffs.

Formatting on save is synchronous, and past its timeout conform gives up
without saying anything — measured with 900 KB of YAML, saved unformatted and
unmentioned. So a buffer over 512 KiB is skipped out loud instead, with
`<leader>xf` left to format it asynchronously. What is measured is the buffer,
not the file: the decision is made before the write, so the file still holds
the previous version, and a buffer that has never been saved has no file to
measure at all.

Terraform needs a terraform CLI                 *chroma-nvim-formatting-tf*

The fallback does not rescue a missing binary. `terraform_fmt` needs the
`terraform` executable, and terraform-ls is not a substitute — it shells out to
`terraform fmt` itself and replies:
>
    Terraform (CLI) is required. Please install Terraform or make it
    available in $PATH
<
Either CLI will do. The formatter is chosen when the buffer is written, by
asking conform which of `terraform_fmt` and `tofu_fmt` can actually run —
terraform first, so nothing changes for anyone who has it, and `tofu_fmt` on a
machine that has only OpenTofu. The question is asked at write time rather than
at startup, because the answer belongs to the machine and can change while
Neovim is running.

Terraform files stay unformatted only when neither is on your PATH. That is a
machine prerequisite; no editor configuration can work around it, and
`:checkhealth chroma` reports it.

Turning it off ~
>
    :FormatDisable      stop formatting on save, globally
    :FormatEnable       resume, globally
    :FormatDisable!     stop, for the current buffer only
    :FormatEnable!      resume, for the current buffer only
    <leader>xF          toggle globally
    <leader>xb          toggle for this buffer
<
Useful when editing a repository whose formatting you do not want to churn.

12. LINTING                                               *chroma-nvim-linting*

nvim-lint covers what the language servers do not. It runs on write, on read,
and on leaving insert mode; `<leader>xl` runs it immediately.
>
    yaml            yamllint      fast — also runs on leaving insert mode
    dockerfile      hadolint      fast — also runs on leaving insert mode
    yaml.ansible    ansible_lint  on write and on demand only
    GitHub Actions  actionlint    on write and on demand only
<
GitHub Actions workflows keep the plain `yaml` filetype rather than getting one
of their own. Giving them a dedicated filetype would take them out of yamlls's
filetype list and lose schema validation, which is most of the value of editing
them in an editor at all. actionlint is therefore selected by matching the
path `.github/workflows/*.yml` instead.

Ansible linting waits on the `yaml.ansible` filetype, which arrives with
nvim-ansible in the DevOps layer.

Why tflint is not here                              *chroma-nvim-linting-tf*

tflint ships an LSP mode and nvim-lspconfig exposes a config for it, so
installing it through Mason already starts it as a language server that
attaches to Terraform buffers. Registering it with nvim-lint as well would
report every finding twice.

14. ANSIBLE                                               *chroma-nvim-ansible*

An execution planner, not a playbook runner. `<leader>ar` asks what to run,
asks Ansible what your answers mean, shows the exact command, and starts it
only when you say so.

Status: BETA. It is covered by the test suite and everything below describes
current behaviour, but it has not been through an external audit. The full
design, with the measurements each rule rests on, is in
`doc/chroma-ansible-design.md`.

Component `ansible`. It needs `ansible-playbook` and `ansible-inventory`, both
of which ship in ansible-core.

Nothing is inferred from the buffer. The buffer is offered as one row in the
first picker and is never the decision — that distinction is the whole reason
this key exists again after the old `<leader>ar` was removed.

The steps                                           *chroma-nvim-ansible-steps*
>
    playbook -> working directory -> inventory -> tags -> limit
             -> overrides -> targets -> preview -> confirmation -> run
<
Escape, a dismissed picker, an empty answer and a selection you never made all
end the run. None of them skips a step.

The working directory is asked for, and it matters: Ansible reads `ansible.cfg`
from the current directory and does not search upward, so that one choice can
decide `roles_path`, the default inventory, vault settings and become defaults.
Chroma offers Neovim's directory, the playbook's own and any ancestor holding
an `ansible.cfg`, marks which of them have one, and freezes what you pick.
`:cd` afterwards moves the editor and not the run.

Inventory is a list, in your order, never sorted: `-i` may be given several
times and the order decides which definition of a host wins. `Use Ansible
configuration` means exactly one thing — no `-i` is passed at all.

Before Ansible runs                                  *chroma-nvim-ansible-gate*

Choosing a file in a picker never starts anything. Before the first Ansible
subprocess of a run, Chroma names the working directory, the playbooks and the
inventory sources and asks whether it may inspect them. The default is no.

That question is not ceremony. An inventory may be an executable script, an
inventory plugin may contact EC2, VMware, LDAP or a CMDB, and an `ansible.cfg`
in the working directory decides which callback plugins, libraries and roles
Ansible loads.

One yes covers every introspection call of that run, and nothing else. It is
bound to the three values the prompt printed: change the directory, the
playbooks or the sources and you are asked again. It is not remembered between
runs, and it is not the confirmation that starts the playbook.

What Ansible is asked                          *chroma-nvim-ansible-inspection*
>
    ansible-inventory --graph       groups, hosts and who is inside whom
    ansible-playbook  --list-tags   the tags the playbooks report
    ansible-playbook  --list-hosts  what this run would address, right now
<
Chroma parses no YAML. Ansible is the authority on what an inventory and a
playbook mean.

`--graph` rather than `--list`, deliberately: `--list` prints every host
variable in plaintext and no flag suppresses them. What is kept is group names,
host names and the hierarchy. No output from any of these subprocesses is
written to a message, a notification or a file.

The tag list is what Ansible reported, which is not the same as every tag: tags
inside dynamically included files do not appear. `Custom tag...` is always
offered, and it is how those are reached rather than a fallback.

Failure here does not stop the run. Each failed inspection shows Ansible's own
output and offers a way to carry on describing the run by hand — retry, no
filter, a value typed in, or cancel. Only three things end the planner: no
`ansible-playbook`, a playbook that cannot be read, and a working directory
that is not one.

Limits and overrides                                *chroma-nvim-ansible-limit*

`No limit` emits nothing. It is not `-l all`: the playbook's own `hosts:` stays
the authority, and `-l all` would override it. A custom pattern reaches Ansible
byte for byte — `webservers:&production` is Ansible's to interpret, and there
is no shell anywhere in this module.

Every CLI option is inherit-or-override, never on or off:
>
    Inherit                  nothing is passed
    Remote user deploy   -u deploy
    Become enable           -b
    Ask become password     -K
    Ask vault password      --ask-vault-pass
<
`-b` and `-K` are separate questions, because become may be enabled by the
playbook and the password still has to be asked for. And the preview says `CLI
become override`, not `Become = yes`: command-line options do not outrank
playbook keywords and variables in every case, so a stronger word would be a
claim Chroma cannot make.

Check mode is Ansible's semantics rather than a guarantee from Chroma — a task
may set `check_mode: false` and act anyway. Diff mode is off unless you turn it
on, and the row that turns it on says why: it can print file contents.

Chroma never collects, stores or logs a password. `-K` and `--ask-vault-pass`
ask Ansible to prompt in the terminal it runs in.

The preview                                       *chroma-nvim-ansible-preview*

The last screen lists every decision and then the argument vector itself, one
argument per line, numbered from zero, with `argv[0]` resolved to the path that
will start. Nothing joins them into a command line: the array never passes
through a shell, and a rendering joined with spaces misrepresents any argument
holding a space or a quote.

`Targets reported now` is a snapshot and never a promise. With dynamic
inventory an autoscaling group can change between the preview and the run;
what Chroma guarantees is the `argv`, the directory and the environment.

The run opens in a terminal that survives every exit status, including zero,
so a playbook that succeeded is still there to read. Prompts from Ansible —
`BECOME password:`, an SSH passphrase — are answered in that terminal.

Repeating                                          *chroma-nvim-ansible-repeat*

`<leader>aR` goes straight to the final preview with the last invocation's
decisions and still asks. It runs nothing by itself.

It re-resolves `ansible-playbook` and re-checks the directory and the
playbooks, and refuses if any of them has moved: repeating an absolute path
recorded an hour ago would run a program nobody chose. The previous run's host
count is never repeated as though it were still true; the row reads `not
refreshed`.

Session memory only. Neovim restarts to a clean state, and no password, host
variable or vault content is kept anywhere.

What this is not                                   *chroma-nvim-ansible-limits*

It does not run a wrapper. `make ansible-prod`, `uv run ansible-playbook` or a
company CLI are what Project Tasks are for (|chroma-nvim-tasks|), and there is
no bridge in either direction: a task declaring `ansible-playbook` in its
`argv` is a task, not a plan this planner will accept.

It selects one playbook, though the model carries a list. It offers no
multi-select of hosts, because combining two hosts means inventing a pattern
and whether that is a comma or a colon is yours to decide. It offers
`--ask-vault-pass` but not vault ids yet. It writes nothing to disk, and there
is no configuration file: configuration may one day make the workflow shorter,
and may never be what unlocks it.

15. ANSIBLE VAULT                                           *chroma-nvim-vault*

`lua/chroma-vault/` is our own plugin, written because the survey found no
maintained candidate: every existing one is a single-person project of 0–7
stars, the most visible untouched since 2023. It depends on nothing else in
this configuration and can be moved to its own repository unchanged.

Status: STABLE. It is in use, covered by the test suite, and its safety model
has been through eleven external audits; the findings of the last one are all
answered. Everything below describes current behaviour, not intent.

Commands ~
>
    :VaultReveal       show the value under the cursor, file untouched
    :VaultEncrypt      encrypt the selected lines in place (needs a range)
    :VaultEncryptFile  encrypt the whole buffer
    :VaultDecryptFile  decrypt the whole buffer in place
    :VaultView         read an encrypted file without decrypting the buffer
    :VaultRekey        re-encrypt this file under another configured vault id
    :VaultStatus       report where the password will come from
    :VaultReload       re-read ansible.cfg after changing it
<
Mapped under the Ansible group: >

    <leader>av   reveal (normal) / encrypt selection (visual)
    <leader>ae   encrypt file        <leader>ad   decrypt file
    <leader>aw   view                <leader>ak   rekey
    <leader>aV   password source
<
Encrypting `db_password: hunter2` gives back `db_password: !vault |` with the
ciphertext indented beneath it, ready to commit. Revealing opens a float that
closes with `q`.

Encrypting a value in place                        *chroma-nvim-vault-inline*

`:VaultEncrypt` encrypts the selected value and nothing else. The file stays
what it was — an ordinary buffer, written by Neovim's own `:write` — so the
protections described under |chroma-nvim-vault-safe| are not what is happening
here. They belong to buffers this plugin creates or takes over.

Said plainly: the plaintext was in that file before you encrypted it, and
encrypting the value does not go back for the copies that already exist. This
configuration keeps persistent undo on, so the file's undo history under
stdpath("state") may hold the value in the clear; so may a backup copy from an
earlier write, and so may a register, ShaDa or the system clipboard
(|chroma-nvim-vault-limits|). Nothing here scrubs any of them.

The two encrypt commands are different operations, not two sizes of one: >

    :VaultEncrypt      encryption of a value
    :VaultEncryptFile  a security transition of a whole file
<
The second deletes the file's undo history (|chroma-nvim-vault-conversion|),
attaches this plugin's writer and owns every write from then on. Use it when a
plaintext secrets file is becoming a vault. Use `:VaultEncrypt` for a value
inside a file that stays what it was — `group_vars/all.yml` holding one secret
among ordinary variables.

Attaching the whole-file writer to such a file is deliberately not done. It
would not be a smaller version of that transition: the whole file would get its
own BufWriteCmd, atomic replacement, a mode normalised to 0600 and a new inode,
because of one value in it. So the limitation is documented rather than papered
over.

Transparent editing                             *chroma-nvim-vault-transparent*

A file whose first line is `$ANSIBLE_VAULT` is decrypted when opened and
re-encrypted when written. Editing a vault is therefore ordinary editing: `:w`
means what it always means, and the file on disk is never plaintext.

The write hook is attached only to buffers this plugin has decrypted. An
earlier version registered it globally with a fallback for everything else,
which is a takeover of `:write` for the entire editor — it broke on the first
scratch buffer that was saved.

It is attached before the plaintext is put in the buffer, not after, and the
same holds for `:VaultDecryptFile`. Decryption happens into a Lua string first;
the buffer is only filled once the hook that protects it is in place. If any
step fails the buffer still holds the ciphertext it was opened with, which is
the safe half of the failure. The step that actually fails in practice is not
the hook but filling the buffer: a 'nomodifiable' buffer refuses it.

The marker saying a buffer holds plaintext is set last, and cleared whenever
the file is re-read. `:edit!` reloads the ciphertext but keeps buffer
variables, so a marker set by an earlier decrypt would otherwise describe a
buffer that no longer holds plaintext. The writer checks what the buffer
actually contains before re-encrypting it.

Turn it off with: >
    require("chroma-vault").setup({ transparent = false })
<
Several vault ids                                 *chroma-nvim-vault-ids*

With more than one id in `vault_identity_list`, ansible refuses to guess which
to encrypt with:
>
    The vault-ids dev,prod are available to encrypt.
    Specify the vault-id to encrypt with --encrypt-vault-id
<
Set `vault_encrypt_identity` in ansible.cfg and it is used silently. Without
it, you are asked which one to use each time.

Every path that encrypts asks the same question: `:VaultEncryptFile`, the write
of a transparently decrypted buffer, and `:VaultEncrypt` on an inline value.
The inline one used not to, so with several identities configured it ran
ansible without an answer and ansible refused.

Dismissing the list cancels the operation rather than falling back to a
default. Nothing runs, the buffer is untouched, and a write refused this way
says so and leaves the buffer modified.

Rekeying                                         *chroma-nvim-vault-rekey*

`:VaultRekey` re-encrypts the current file to another identity from
`vault_identity_list`. It works relative to a configured Vault identity, not an
arbitrary one-off password.

That restriction is the point. A password typed once lives only in a temporary
file that is deleted immediately, and ansible resolves credentials from
ansible.cfg — so a file rekeyed to it could not be opened again by anything,
including this plugin. With no `vault_identity_list` configured the command
refuses and says what to set up, rather than offering a password it cannot make
persistent.

The new id is recorded in the file header (`$ANSIBLE_VAULT;1.2;AES256;prod`),
which is how ansible finds the right secret next time the file is opened. The
identity the file currently uses is marked "(current)" in the list.

The check is made against the file on disk, not the buffer: with transparent
editing the buffer holds plaintext, and an earlier version inspected it and
therefore refused on exactly the files this command is for.

A file with more than one hard link is refused before anything else happens,
including the question about which identity to use. This is the same policy the
writer applies (|chroma-nvim-vault-writing|), but the consequence here is worse:
ansible-vault does not replace the file, it overwrites the inode in place and
then unlinks it. Through a hard link that destroys what the other name holds
rather than leaving it stale. Measured against ansible-core 2.21.2 — after
rekeying one of two names, the other was random data that no longer decrypted.

Converting a plaintext file             *chroma-nvim-vault-conversion*

`:VaultEncryptFile` turns the current buffer into a vault. On a file that has
never been encrypted this does more than replace the buffer's contents, and it
has to.

'undofile' is switched off for the buffer, along with 'swapfile' and
'modeline'. That stops new undo files appearing but does not remove one that
already exists, and an existing undo file holds every earlier state of the
buffer — the secret, in the clear, under `stdpath("state")`, surviving reboots.
So the conversion deletes it.

That is deliberate data loss: converting a plaintext file to a Vault discards
its persistent undo history. If the undo file cannot be deleted the conversion
does not happen at all, and persistent undo stays off for the buffer; finishing
would mean reporting a vault while a plaintext copy of it stayed behind.

The safe writer is attached before the buffer changes, so the first `:write`
after the conversion goes through the same path as every other Vault write —
conflict detection and atomic replacement. It also means Neovim's own write
never runs for this buffer, and so never makes its usual backup copy of the
file it is replacing. 'backup' and 'writebackup' are global options and cannot
be turned off for one buffer; taking the write over is what replaces them.

Writing                                          *chroma-nvim-vault-writing*

A vault is replaced by writing a sibling file and renaming over the target, so
an interrupted write leaves the old contents rather than a truncated file.
Symlinks are followed: the link survives and the file it points at is what
changes.

A decrypted vault is written back to the file it came from and nowhere else, so
`:w elsewhere`, a partial `:1,10w elsewhere`, an append and `:saveas` are all
refused. `:saveas` leaves one loose end: Neovim renames the buffer before the
write hook runs, so the buffer ends up under the new name even though nothing
was written to it. Measured, and left as it is — raising from BufFilePre does
not abort the rename, and setting the name back makes Neovim treat the buffer as
never read from that file, so the next `:w` fails with E13. The vault on disk is
untouched; `:edit! {the original}` puts the buffer back where it belongs, at the
cost of the changes it held.

The rename is followed by an fsync of the directory it changed. Renaming is
atomic against a process that dies, but the entry it wrote is not on the disk
until the directory is flushed, so a power cut could otherwise leave the old
contents behind after a write that reported success. If that fsync fails you
get a warning naming the file, not a failed write: the vault is already in
place, so there is nothing to undo and the buffer is not left modified over
work that reached the disk.

That sibling is named after the process and the monotonic clock, and created
with a flag that refuses an existing name. The clock is not decoration: a name
made from the process id alone comes back once the system reuses that id, and
a file left behind by a session that crashed would then make every write of
that vault fail. If a failed write cannot take its sibling away with it, the
error says so and names the file — it holds ciphertext, not plaintext, so it
is litter rather than a leak.

Hard links are refused. rename() replaces one name, and every other name for
that inode would keep the old contents — so instead of letting two names
silently diverge, the write stops and says how many links there are. Writing in
place would keep them and give up the protection against a truncated vault.

The same refusal guards `:VaultRekey` (|chroma-nvim-vault-rekey|), which is the
other operation that replaces a Vault file. One policy, asked in one place: an
operation that mutates a Vault does not get to decide for itself whether the
other names for that file matter.

Vault buffers carry 'noswapfile' and take over `:write`, which removes both of
Neovim's protections against two editors clobbering each other. The replacement
is a fingerprint — mtime including nanoseconds, size, inode and device — taken
when the file is read and compared before it is written. A file changed, or
atomically replaced, underneath the buffer refuses the write. Whole seconds and
size alone were not enough: two writes inside the same second producing the
same number of bytes compare equal on both.

Where the password comes from                          *chroma-nvim-vault-pass*

Ansible's own configuration is consulted rather than reimplemented: the plugin
runs `ansible-config dump` in the project directory and reads the resolved
`vault_password_file` and `vault_identity_list`, along with which file supplied
them. `:VaultStatus` prints the answer.

When ansible already knows the password, no credentials are passed on the
command line at all — the subprocess simply runs in the right directory.
Passing them again registers a second identity under the same label and ansible
refuses with "The vault-ids default,default are available to encrypt".

With nothing configured, you are prompted; the password is then written to
$XDG_RUNTIME_DIR with mode 0600 and unlinked as soon as the command returns.

Removing it is attempted whether the command succeeded, failed, or never
started at all. Starting is the case that used to be missed: `vim.system`
raises before it spawns anything if the directory the command would run in has
been removed, and that exception skipped the removal, leaving the password
staged for the rest of the session. The removal is also checked rather than
assumed — the synchronous libuv calls report failures by returning `nil, err`
rather than raising, so wrapping one in `pcall` answers "removed" whether or
not it was. If it cannot be removed you get an error naming the exact path, so
you can delete it yourself.
Where that directory is memory-backed the file never reaches a disk at all, but
that is the platform's doing and is not something checked here. What is checked,
and what the XDG specification requires, is |chroma-nvim-runtime-dir|.

The runtime directory                             *chroma-nvim-runtime-dir*

$XDG_RUNTIME_DIR is validated before anything is written into it, by both
`chroma-vault.nvim` for staged passwords and `chroma-terraform.nvim` for plan files.
It must be set, absolute, a directory, owned by the current user, and mode
0700 — what the XDG specification requires of it. Each plugin then uses its own
0700 subdirectory, created if missing and checked either way.

The variable is checked rather than trusted because it is a variable: anything
able to set it can redirect these writes somewhere readable. Checking only that
it was set, which is what both did before, accepted a world-readable directory
without a word.

If the check fails, the operation is refused. Neither plugin falls back to
/tmp. `:checkhealth chroma-vault` and `:checkhealth chroma` report the result
of the same check, so the failure is visible before it is hit.

It is worth being exact about what that directory guarantees, because it is not
"tmpfs" and it is more useful than that word suggests. The specification
requires it to be owned by you and mode 0700, to be on a local file system, to
exist from your first login to your last logout, and — this is the part that
matters here — its contents MUST NOT survive a reboot or a full logout/login
cycle. Its files may also be cleaned up periodically. Residence in memory is
not among the requirements: the specification says only that the directory
"might reside in runtime memory", and nothing here checks the file system type.

So on a system that puts the runtime directory on a disk, these files are
written to that disk. They are still private, still session-scoped, and still
gone by the next boot; they are not guaranteed to have avoided the platter.

What it protects against                               *chroma-nvim-vault-safe*

The encryption is one subprocess call. The work is in everything around it:

  Plaintext never appears in argv. `ansible-vault encrypt_string` accepts the
  string as a positional argument, which would publish the secret to anyone
  running `ps`. Given no positional argument it reads stdin, which is what
  this plugin does.

  Plaintext never reaches the undo file. This configuration enables 'undofile'
  globally, so a revealed secret would otherwise be written verbatim to
  stdpath("state")/undo and survive reboots. Buffers holding plaintext are
  created with 'noundofile', 'noswapfile', buftype=nofile and bufhidden=wipe.
  This covers the buffers this plugin creates or takes over; a value encrypted
  in place inside an ordinary file is a different case, stated separately in
  |chroma-nvim-vault-inline|.

  Ciphertext is treated as public, because it is. That is what frees stdin for
  the plaintext.

  Vault files are replaced by this plugin's own writer, never by Neovim's.
  That is where the conflict check and the atomic replacement live, and it is
  also why no backup copy of the file being replaced is made. The replacement
  creates a new inode with mode 0600: custom ACLs, extended attributes,
  security labels and group ownership are not guaranteed to survive it. For a
  secrets file 0600 is the right default, so it is normalised rather than
  merged.

  Hard links are refused rather than broken, by writes and by `:VaultRekey`
  alike (|chroma-nvim-vault-writing|).

  Converting a plaintext file to a Vault deliberately discards that file's
  persistent undo history (|chroma-nvim-vault-conversion|).

  A prompted password is written only into the validated private runtime
  directory (|chroma-nvim-runtime-dir|), never to /tmp, and is unlinked as soon
  as the command returns.

Verified by searching for a known secret after a full encrypt/edit/write/reopen
cycle: nothing under stdpath("state"), nothing in the undo directory, nothing
beside the file, and no leftover staged password in $XDG_RUNTIME_DIR.

What the tools see                                   *chroma-nvim-vault-tools*

A decrypted vault is an ordinary buffer with a detected filetype, which is what
makes editing it ordinary — and also what invites everything this configuration
attaches to a YAML file. A language server is handed the whole buffer on
didOpen, and nvim-lint feeds linters on stdin, so without a rule the plaintext
would reach yamlls and yamllint as a matter of course.

So while a buffer holds plaintext: linters are not run for it, neither
format-on-save nor `<leader>xf` touches it, language servers are detached from
it — including any that attach later, because setting the filetype is what
invites them and it happens after the plaintext is in place — and gitsigns
neither attaches nor stays attached.

Completion is on the list for a third reason: blink's buffer source offers
words from every visible buffer, so a vault open in a split fed its secrets to
the file beside it as completion candidates, and accepting one put the secret
somewhere nothing here protects.

Gitsigns is on that list for a different reason from the others. Staging a hunk
does not write the working tree; it writes `.git/index` and a blob object from
the buffer's own lines. A decrypted vault staged that way puts the secret into
git, past the writer, the atomic replacement and every other guard, which are
all about the file. Measured before the guard existed: the index held the
plaintext and the ciphertext was gone.

What that does not close: a server can be handed the buffer between the filetype
being set and the detach, which is the same event loop iteration but not the
same instant. The plugin cannot veto an attach, only undo one. If that matters
for your threat model, the answer is the stricter workflow below rather than a
setting — and note that this is about local subprocesses, not the network.

What it does not protect against                     *chroma-nvim-vault-limits*

Registers, ShaDa, the system clipboard and external clipboard managers are all
outside the guarantee above, and the reason is the same for each: they are
global machinery, not properties of a buffer, so a plugin cannot narrow them to
Vault buffers without deciding how the rest of the editor behaves.

This configuration sets `clipboard=unnamedplus`, which routes unnamed-register
operations through the system `+` clipboard. That is not only `yy`: ordinary
editing — `dd`, `dw`, `cw`, `x` — uses the unnamed register too, so plaintext
from a decrypted vault can reach the system clipboard without anyone deciding
to copy it. Neovim's default 'shada' includes `<50`, which persists register
contents between sessions.

'noundofile' and 'noswapfile' do not address any of this. They are about what
Neovim writes for a buffer; these are about where the text goes once it is in a
register.

Stricter workflow                                    *chroma-nvim-vault-strict*

For work where that matters, use a separate session rather than a setting: >

    nvim -i NONE secrets.yml
<
`-i NONE` disables both reading and writing ShaDa, so register contents do not
outlive the session. Drop `clipboard=unnamedplus` for that session as well, or
yanks and deletes still reach the system clipboard.

Two things this does not do, stated so it is not read as more than it is:

  It has no control over a clipboard manager. Anything that already reached the
  clipboard may have been copied by one, and quitting Neovim does not take it
  back.

  An explicit `"+y` still copies a secret out. That is the user asking for it,
  and no session setting turns a deliberate copy into a refused one.

This is a workflow rather than a plugin option on purpose. 'clipboard' and
ShaDa are global; a mode that changed them per Vault buffer would have to
handle several vault buffers at once, nested entry and exit, and restoring
state on every path out — and would be most likely to fail exactly where it was
trusted most.

`:checkhealth chroma-vault` reports which of this applies to your setup.

16. TERRAFORM                                           *chroma-nvim-terraform*

`lua/chroma-terraform/` is our own runner, deliberately thin. The survey found most of
the originally planned scope already covered: formatting is conform's
`terraform_fmt`, validation is tflint running as a language server. What was
missing was running a plan and applying it without leaving the editor.

Status: STABLE. It is in use, covered by the test suite, and its safety model
has been through eleven external audits; the findings of the last one are all
answered. Everything below describes current behaviour, not intent.

The safety model                              *chroma-nvim-terraform-safety*

Naive runners call `terraform apply -auto-approve`, which applies a plan nobody
read, computed at a moment nobody chose. This one cannot do that.
>
    1. :TerraformPlan   writes the plan to a file and shows it
    2. you read it
    3. :TerraformApply  applies THAT FILE
<
Terraform documents the consequence: passing a saved plan file to `apply` means
"Terraform performs the operations in the saved plan without prompting you for
confirmation" — the file is the approval. So apply never needs -auto-approve.

What that does and does not promise, precisely:

The saved plan fixes the exact planned action set. The runner also preserves
the selected executable and, when `strict_aws_identity` is enabled, verifies
the AWS account and principal before apply. External infrastructure,
credentials and remote state may still change independently between plan and
apply.

An earlier version of this file said drift between reading and applying was
impossible. It is not, and the sentence is gone: what is fixed is the action
set, the program that carries it out and — optionally — who it runs as.

Destroy is not a separate, scarier command. `:TerraformPlanDestroy` produces a
plan to read like any other, applied through the same step. Nothing in this
plugin destroys anything without a plan having been reviewed first, and the
confirmation for a destroy plan requires typing `destroy` — `yes` is rejected.
Verified.

The pinned executable                        *chroma-nvim-terraform-executable*

Whichever of `terraform`, `tofu` or `terragrunt` applies to the directory is
resolved once, when the plan is made, and the resolved path is recorded with
it. The apply runs that path.

A directory holding terragrunt.hcl or terragrunt.stack.hcl is terragrunt's;
otherwise `terraform` is preferred and `tofu` used where only tofu is
installed. With neither installed the command refuses and says so — naming both
rather than one, since which of the two was meant is not something to guess.

If it has since disappeared the apply is refused rather than resolving the name
again. PATH can change, terraform can be uninstalled leaving tofu to answer for
it, and a terragrunt.hcl can appear in the directory in between — none of those
three produce the plan that was reviewed.

When a plan counts as reviewed                  *chroma-nvim-terraform-review*

A plan is considered reviewed only after the review view is displayed
successfully. If review rendering fails, the new plan artifact is deleted and
any previously reviewed plan for that directory is invalidated.

The window can genuinely fail to open — E36, when the layout leaves no room for
a split. Recording the plan anyway would mean a plan nobody saw was appliable,
so nothing appliable survives a review that did not happen. `:TerraformPlan`
works again immediately; only the unread plan is lost.

One operation at a time                     *chroma-nvim-terraform-concurrency*

At most one of planning, applying and initializing is true for a directory at a
time.

Planning is the one that can hold several claims at once. Two plans may overlap
by design — the generation counter decides which of them may become the reviewed
plan — and the directory is held until the last of them has finished, not the
newest. It used to hold a single generation, so a newer plan finishing released
a directory an older terraform was still running in, and `init`, which exists to
refuse exactly that, let itself through.

An apply cannot be taken back, so while one runs in a directory the plugin
refuses a second apply, a new plan, an `init` and a `discard` there. The first
two would hand the running apply's plan file to another process or delete it;
init would rewrite `.terraform` underneath it.

`init` is serialised the same way. While one runs, a plan, an apply, a second
init and a `validate` are all refused; and while a plan runs, an init is
refused in turn. It rewrites `.terraform/` — providers, modules, backend
configuration — which a plan reads and which supplies the schemas `validate`
checks against. Verified before this was added: an init started during a plan
ran concurrently with it, and two inits could rewrite the directory at once.

Starting an `init` also discards the reviewed plan. It can bring in a new
provider version, a changed module source or a different backend, and a plan
computed before it describes none of them.

`validate` is otherwise not refused: outside an init it reads configuration and
provider schemas, not state, so it cannot collide with a plan or an apply.

A directory is claimed before the process starts, so every path that fails to
start one releases it again — including the one where starting raises rather
than returns. `vim.system` raises before it spawns anything if the directory
has been removed (ENOENT) or replaced by a file (ENOTDIR), which is reachable
because the directory is claimed before the identity lookup and the process is
started after it. That exception used to escape the command that took the
claim, and every later operation there answered "a plan is running" until
Neovim was restarted. Starting a process is now an ordinary failure the runner
reports, not an exception; the same applies to the identity lookup, whose
failure to start is reported as an unknown identity.

Two plans started in the same directory are ordered by when they were
requested, not by which process finished first. The older one discards its own
output rather than replacing a newer plan you have already read.

Asking for a plan invalidates the one already reviewed for that directory, at
the moment you ask rather than when the new plan succeeds. Requesting a new
plan says the old picture is out of date, so it stops being appliable straight
away: while the new plan runs, `:TerraformApply` says so and refuses, and if
the new plan ends in "No changes" or an error there is nothing to apply
afterwards either. Without this the previous plan stayed reachable — verified
against the module, an apply after a plan reporting no changes was handed the
plan from before it.

AWS credentials                            *chroma-nvim-terraform-credentials*

The plan file fixes what terraform will do, not who it does it as. Credentials
come from the environment, which `:AwsProfile` changes on the Neovim process.
There are two layers, and they are not the same check.

The first is always on: AWS_PROFILE and the region are recorded with the plan
and compared before apply. A difference refuses.

That is a proxy, and a weak one. With the profile name unchanged it still
misses new static credentials, an SSO session refreshed against a different
account, an edited ~/.aws/credentials, the same profile now assuming a
different role, and credential environment variables, which take precedence
over the profile entirely.

The second closes that, and is off by default: >

    require("chroma-terraform").setup({ strict_aws_identity = true })
<
`strict_aws_identity` is disabled by default. When enabled, `aws sts
get-caller-identity` is executed during plan and again before apply. Both the
AWS account ID and principal ARN must match.

It fails closed. Every way the question can go unanswered — no `aws` on PATH, a
spawn that never starts, a non-zero exit, an answer that is not JSON, an answer
without an account — refuses the operation rather than continuing without a
binding. A plan that cannot be bound to an identity is the plan this option
exists to prevent: it compares equal to any other unidentified plan, so the
check at apply time would pass by knowing nothing on both sides.

A missing `aws` is not read as "this is not an AWS project". The AWS provider
reads ~/.aws/credentials and the environment by itself and needs no CLI, so the
absence of one says nothing about what terraform is about to talk to. If a
directory genuinely has nothing to do with AWS, turn the option off for it
rather than relying on the check to skip itself.

A refused apply keeps the reviewed plan: nothing about the plan has been shown
to be wrong, so fixing the credentials and applying again is the whole
remedy.

The answer is never cached. A cache is a way of being told which credentials
were in effect earlier, which is exactly what this is guarding against — so the
cost is a network round trip on every plan and every apply, and that cost is
why it is opt-in rather than the default.

No `aws` on PATH is treated as "not an AWS project" and skipped without
comment. An `aws` that is present and refuses is reported at plan time, because
the plan is then recorded without the protection the option was enabled for.

Commands and keys ~
>
    :TerraformInit          <leader>ti
    :TerraformValidate      <leader>tv
    :TerraformPlan          <leader>tp
    :TerraformApply         <leader>ta
    :TerraformDiscard       <leader>td   throw away a reviewed plan
    :TerraformPlanDestroy   no mapping, on purpose
<
Terragrunt is used automatically in any directory containing terragrunt.hcl,
because running plain terraform there would ignore the generated configuration.

Exit codes and plan files                        *chroma-nvim-terraform-plans*

`plan` runs with -detailed-exitcode, which distinguishes "no changes" (0) from
"changes present" (2). With no changes the plan file is deleted immediately and
you are told so, rather than being offered an empty apply.

Plan files can quote sensitive variable values, so they are written to
$XDG_RUNTIME_DIR — private, session-scoped, see |chroma-nvim-runtime-dir| — and
chmod'ed to 0600 as soon as terraform has created them. Terraform writes them
under the ambient umask; they came out 0644 in testing, which is why this is
done explicitly.

A plan file is removed after the apply that spent it, when a newer plan
supersedes it, when a review cannot be shown, and on :TerraformDiscard. Every
one of those removals is checked rather than assumed — fs_unlink reports failure
by returning an error, not by raising one — and a file left behind is named, so
you can remove it yourself.

On exit, the runner attempts to remove all reviewed and currently known pending
plan artifacts. Pending covers a plan whose command is still running: terraform
writes the file, so it can exist well before the callback that would record it,
and a session ending in that window used to leave it behind. What a subprocess
writes after Neovim has gone is out of reach — it outlives the session that
started it, and nothing here terminates it.

If that chmod fails the plan is deleted rather than saved: a plan the runner
could not protect is not one it will offer to apply.

The reviewed plan is bound to its contents *chroma-nvim-terraform-integrity*

A SHA-256 of the plan file is taken after it is protected and again after the
review window has been shown. The two must match, or the plan is discarded —
so the digest that gets recorded is one that survived the review step. Before
an apply the file is hashed once more and compared against the recorded digest.
A difference refuses the apply and discards the plan; so does a file that can
no longer be read.

That check runs before the identity lookup and before the confirmation prompt,
because there is nothing to approve if the artefact is already invalid. It runs
again immediately after you confirm, and that is the one that closes the gap:
the lookup waits on the network and the prompt waits on a person, and a check
made only before them says nothing about the seconds that follow. A difference
there refuses the apply, discards the plan and names the window it happened in.

The digest covers the whole file. It is read to the end rather than to a size
measured beforehand, so a read that returns fewer bytes than asked for cannot
be hashed as though it were everything.

What this is: an exact statement that the bytes handed to apply are the bytes
that were reviewed, and detection of accidental replacement or corruption.

What it is not: protection against a hostile process running as you. The
runtime directory is 0700, so other users are already out; a process with your
own uid could change the file between the check and the apply, and no hash here
would stop it. Such a process could also rewrite this plugin.

$XDG_RUNTIME_DIR is validated rather than trusted; see
|chroma-nvim-runtime-dir|. If it fails that check the plugin refuses to plan
rather than writing a plan anywhere else.

Extra arguments                              *chroma-nvim-terraform-arguments*

Five lists, all empty by default: >

    require("chroma-terraform").setup({
      global_args   = {},   -- before the subcommand
      init_args     = {},
      validate_args = {},
      plan_args     = {},
      apply_args    = {},
    })
<
`global_args` goes where terraform's grammar says global options go — before
the subcommand, as in `terraform [global options] <subcommand> [args]`. The
per-command lists go after the runner's own flags, so a later flag wins where
terraform lets it. Positional arguments stay last, because `terraform apply`
expects its options before the plan file.

The options that move a command somewhere else are not passed on. The runner
decides which directory each command runs in, and everything it remembers hangs
off that decision — the saved plan, the generation counter, the concurrency
claims, the AWS context, the path the plan file is written to. A CLI running
elsewhere would leave all of it pointing at a directory nothing ran in. Dropped
with an error: >

    -chdir                     terraform
    --working-dir              terragrunt
    --terragrunt-working-dir   terragrunt, before its CLI was redesigned
<
The terragrunt spellings take a value, so a split `--working-dir /elsewhere` has
its path dropped as well; left behind it would arrive as a positional argument,
which for `plan` is the directory terragrunt runs in — the same escape by
another route.

The environment is a different matter. `TG_WORKING_DIR` and terraform's own
`TF_*` variables reach the subprocess through the environment this Neovim was
started with, and nothing here filters that. If a directory has to be
overridden, the honest place is the shell you launched the editor from, where
it applies to everything rather than silently to this runner alone.

Four per-command options are dropped for the same kind of reason — the runner
sets them and relies on their values:

    plan   -out                the plan would land somewhere else, and the file
                               this plugin saves, protects and applies would
                               never have been written
    plan   -destroy            the plan would destroy while the runner recorded
                               an ordinary one, so the confirmation would ask
                               for "yes" instead of "destroy" and the review
                               window would not be marked
    plan   -detailed-exitcode  the 0/1/2 codes would stop meaning what the
                               runner reads them as
    plan,  -input              prompting would be re-enabled on a subprocess
    apply,                     with no terminal, which does not fail, it hangs
    init

Anything else is passed through untouched. This is not a general blacklist:
options terraform itself rejects with a saved plan, such as `-target` or
`-var`, are left to terraform, whose error says it better.

A rejected option is reported and ignored rather than raised, so a mistake in a
plugin spec does not stop the editor loading. The report happens once, when the
plugin is configured.

17. AWS AND SESSIONS                                          *chroma-nvim-aws*

AWS ~

`lua/chroma-aws/` is ours. The survey found nothing worth adopting: nvim-aws-cli has
no stars and no commit since March 2025, nvimawscli has twelve and manages EC2
instances, which is not what an editor is for.

The scope is one thing: make sure the next `terraform plan` runs against the
account you meant. `:AwsProfile` and `:AwsRegion` set AWS_PROFILE and
AWS_REGION on the Neovim process, so every subprocess inherits them — the
terraform runner, a `:terminal`, a language server. Verified: after setting
them, a subprocess sees the new values.
>
    :AwsProfile   choose from `aws configure list-profiles`
    :AwsRegion    choose from the account, or type one
    :AwsStatus    what the next subprocess will see
    :AwsWhoami    what those credentials actually resolve to
    :AwsClear     put back what Neovim started with
<
`:AwsClear` restores rather than unsets. AWS_PROFILE and AWS_REGION are read
from the environment when the plugin is first set up and put back on demand, so
starting Neovim with a profile exported and then switching leaves that first
profile as what "clear" means. The snapshot is taken by the first `setup` only:
a later one runs after profiles have been switched, and recapturing there would
make the profile you switched to look like where you began.

Profiles come from the CLI rather than from parsing ~/.aws/config, because the
CLI already understands config, credentials, SSO sessions and AWS_CONFIG_FILE.

Regions are not hardcoded — a baked-in list is wrong the day AWS opens a
region. They are read from the account when credentials allow, and typed when
they do not.

`:AwsWhoami` exists because AWS_PROFILE being set is not the same as it
working, and finding that out from a failed apply is expensive.

Sessions                                                 *chroma-nvim-sessions*

persisted.nvim, chosen over auto-session (larger surface, 28 open issues) and
persistence.nvim (no push in nine months). Sessions are per directory and per
git branch: infrastructure repositories tend to keep a long-lived branch per
environment, and the files that matter on `prod` are rarely the ones that
matter on a feature branch.

The dashboard is excluded from what gets saved, so a restored session opens
onto the work rather than onto a stale start screen.

18. PROJECT TASKS                                           *chroma-nvim-tasks*

Chroma does not learn how your infrastructure is run. The repository says it.

`<leader>xr` reads `.chroma/tasks.json`, shows exactly what is about to run,
and starts it once you agree. Nothing is inferred — not from the buffer, not
from its filetype, not from where the editor happens to be.

Status: STABLE, schema 1. It is covered by the test suite, and everything below
describes current behaviour. What schema 1 deliberately leaves out is at the
end of this section.

Tasks belong to `core`, so they are in every installation and there is no
component to switch on.

The order of the steps is itself the contract:
>
    availability -> discovery -> trust -> schema -> picker
                 -> cwd -> argv -> preview -> confirmation -> run
<
Three of those positions are load-bearing. Trust is asked before the picker,
because Neovim's modal on top of a picker is a question about a list you can no
longer see. The directory and the executable are resolved after a task has been
chosen, so one task naming a command this machine does not have cannot hide
every other task in the document. The preview and the executor read one
prepared execution rather than preparing it twice, because a PATH can change
between the question and the answer.

Anything that is not an explicit yes ends in nothing happening.

The document                                           *chroma-nvim-tasks-file*
>
    {
      "schema": 1,
      "tasks": [
        {
          "id": "plan-staging",
          "name": "Plan",
          "group": "staging",
          "cwd": { "mode": "relative", "path": "envs/staging" },
          "argv": ["terraform", "plan", "-out=tfplan"],
          "env": { "TF_IN_AUTOMATION": "1" }
        }
      ]
    }
<
The document has two fields, `schema` and `tasks`, and a task has six:

    id         required    unique in the document
    name       required    what the picker shows
    group      optional    shown as a prefix: "group / name"
    cwd        required    where it runs; an object, see below
    argv       required    a non-empty array of strings
    env        optional    an object of non-empty strings

The picker answers with the task rather than with its label, because the schema
requires ids to be unique and says nothing about names: two tasks may be called
"Plan" and only one of them is the one that was chosen.

`cwd` has two modes in schema 1:

    { "mode": "project" }                    the directory holding .chroma/
    { "mode": "relative", "path": "envs/x" } that directory, plus a path

A `path` written beside `project` is refused rather than ignored. Somebody
wrote it expecting it to be used, and the difference between ignored and used
is which directory an apply runs in.

A document is refused whole, and the refusal names the file, the task and the
field:
>
    .chroma/tasks.json: task "plan-staging": cwd.mode "file" is not supported
<
Strict, for the reason `components/*.json` is strict: a file that decides what
a machine executes is the worst place to be quietly generous. An unknown field
at any level, a duplicated id, a schema that is not 1, a number where a string
belongs, a `null`, an absolute `cwd.path`, an empty `argv` — each is an error
naming itself rather than a task that silently runs something else. `"tasks":
{}` is refused too: an empty JSON object is not an empty array, and asking the
decoder rather than counting keys is what keeps the two apart.

Discovery                                         *chroma-nvim-tasks-discovery*

The search starts at the editor's effective working directory — `getcwd()`, so
a window-local `:lcd` counts — and climbs.

The first entry named `.chroma/tasks.json` ends the search, whatever it turns
out to be. A directory of that name, a broken symlink, a file this user may not
read: each is refused by name, and none is a reason to keep climbing. Stepping
over an unusable entry would hand this project's Run Task to whichever
repository happens to sit above it.

"There is nothing here" and "I was not allowed to look" are two different
answers and only the first continues upward, so an unreadable `.chroma/` is
reported rather than turned into somebody else's tasks running.

Nothing is remembered between runs. A file trusted since the last look, one
just written, one just deleted and a different project all have to be seen by
the next `<leader>xr`.

Trust                                                 *chroma-nvim-tasks-trust*

The file is executable content, and the decision about it is Neovim's, not
Chroma's. The first task in a repository therefore takes two steps.

The prompt that appears is Neovim's own and calls this "exrc: Found untrusted
code", which names a feature nobody asked for, so Chroma prints a line naming
the file just before it appears — and only when it is going to appear.

For a file the choices are ignore, view and deny. There is no allow. Trusting
one means: choose (v)iew, read it, leave the buffer, run `:trust` with no
argument, and press `<leader>xr` again.

Never `:trust <file>`. Neovim's own documentation warns of a TOCTOU risk there
and directs you to view the file first.

The decision is a `sha256` of the exact bytes, so editing the file invalidates
it and the two steps repeat. The trust is in the contents, not in the path.

Deny writes `!` and silences the question. Chroma reports that state rather
than calling into a prompt that would not appear; `:trust ++remove` on the file
undoes it.

One snapshot is authoritative. Chroma reads the bytes, hashes them, and parses
those same bytes — it does not hash a file and then let something read it a
second time, because the contents can change in between and a trusted answer
would then authorise one byte string and hand back another.

The database is `$XDG_STATE_HOME/nvim/trust`, one decision per line. One that
exists and cannot be understood is reported as exactly that: guessing at it
would mean guessing at a security state.

The working directory                                   *chroma-nvim-tasks-cwd*

One invariant covers both modes:
>
    realpath(working directory) is the project root, or inside it
<
Both sides are resolved before they are compared, and compared by path
components. A `..` in the task and a symlink in the repository are covered by
the first; the second is what a textual prefix would get wrong, since
`/project` is a prefix of `/project-evil` and the difference between those two
is the difference between a plan and somebody else's infrastructure.

Neovim's current directory is consulted once, by discovery, to know where to
start looking. After that it has no influence at all: `:cd`, `:lcd`, `:tcd`,
a session plugin or a file manager may move the editor between reading a
preview and agreeing to it, and none of them changes where the task runs.

The command                                         *chroma-nvim-tasks-command*

There is no shell. `argv` is handed to the process as an array, and nothing in
it is expanded, split, quoted or globbed.

Exactly one element changes: `argv[0]` is resolved to the absolute path it
names. That is not Chroma reinterpreting the command, it is the only way the
rest of this holds. Measured on 0.12.4: `jobstart` validates the first element
before it looks at the `env` and `cwd` it was handed, so a bare name is
searched in the editor's PATH and `./deploy` against the editor's directory —
both fail with E475 even when the task's own PATH and working directory hold
exactly what was asked for.

The lookup uses the PATH the child will have, which is the task's override when
it declares one. A name containing `/` is taken as a path, relative ones
against the task's directory. A bare name is searched, and an entry that exists
without being executable is stepped over rather than accepted, which is what a
shell would have done. A directory is never the answer: it passes an execute
check — that is what makes it traversable — so the type is asked as well. An
empty PATH entry means the task's working directory, the same answer `execvp`
gives after the chdir.

Everything after `argv[0]` is copied byte for byte.
`../inventories/dev/hosts.yml` is the program's to interpret against its own
directory, not Chroma's to tidy.

`env` is added to what Neovim inherited rather than replacing it.

The preview                                         *chroma-nvim-tasks-preview*

What is shown is the prepared execution and nothing else: the task, the
resolved directory, the overrides sorted by name, and every argument numbered
from zero as the process will see them — with `argv[0]` as the path that was
found, because that is what will start.

No line joins them into something that looks like a command line. The array
never passes through a shell, and a rendering joined with spaces misrepresents
any argument with a space, a quote or a semicolon in it — and that is the line
people copy. Control characters are escaped, the backslash included, so one
argument stays one visible argument.

The question defaults to No. Escape, a dismissed dialog and an answer that
never arrives are the same answer, and it is the one that runs nothing.

The terminal                                       *chroma-nvim-tasks-terminal*

One Run is one new process, in a terminal of its own.

`<leader>xs` toggles, and finds its terminal by command, directory, environment
and count. A task does the opposite and always opens: a second Run of the same
task would otherwise flicker a window instead of running anything. That
identity has no room for a task id either, so each Run takes the next number of
the session as its count and two tasks running the same command in the same
place stay apart.

The terminal survives the process, whatever it exits with. Automatic closing is
off, because a successful `terraform plan` is precisely the output somebody
opened this to read. The library keeps its own failure notice inside that same
switch, so a non-zero exit is reported by Chroma instead — and the window stays
exactly as it is, with whatever the process printed before it gave up.

Neovim 0.12.3                                       *chroma-nvim-tasks-version*

Chroma's floor is 0.12 and stays there. Project tasks are the one feature that
asks for more, and they ask because they are the one feature that puts Neovim's
trust prompt on screen: `vim.secure.read()` reaches the `view` path whose
command-injection fix landed upstream in 799cbfff8 (2026-05-20). Checked at
each release — absent from v0.12.0, v0.12.1 and v0.12.2, present from v0.12.3.
A security boundary is not built on an implementation without the fix.

Below it `<leader>xr` refuses, names the version it found and says why;
`:checkhealth chroma` reports it before anybody tries. Everything else in
Chroma works on 0.12.

What schema 1 does not have                          *chroma-nvim-tasks-limits*

Each of these was designed and then left out, so that the first version of the
execution model could be proved end to end:
>
    inputs, and ${input.NAME}
    ${file} and ${file_dir}
    cwd.mode = file
    cwd.mode = nearest, with markers
    cwd.mode = prompt, with a directory picker
    global and user-level tasks
    shell tasks, for a command that genuinely needs one
    domain shortcuts that open the picker pre-filtered by group
    run history, and a way back to a previous run
<
They are written down because a list of things nobody got round to and a list
of things somebody decided against look identical six months later.

No task is domain-aware, and that is not on the list. Chroma reads `argv`; it
does not notice that a word in it is `terraform`. |chroma-nvim-terraform| and
|chroma-nvim-vault| are separate features with safety models of their own, and
a task naming the same binary gets none of them.

`CONTRACT.md` beside this file states the invariants, under "The execution
layer"; `DECISIONS.md` says why each is what it is.

19. ADDING A PLUGIN                                        *chroma-nvim-adding*

Before writing any configuration, do the reading. This is rule #1 and it is
not decorative; see |chroma-nvim-rules|.

  1. Check the plugin is alive: last commit, open issues, whether upstream
     points somewhere else. A plugin abandoned two years ago does not go in,
     however many stars it has.
  2. Read its current README and `doc/*.txt`, and its recent releases for
     breaking changes. Assume anything written before Neovim 0.11 is stale.
  3. Check whether something already installed does the job.
  4. Add it to the matching `lua/plugins/<domain>.lua`, with its keymaps in
     its own spec.
  5. Check its default keymaps against |chroma-nvim-zellij|.
  6. Start Neovim, run `:Lazy sync`, then `:checkhealth`.
  7. Commit `lazy-lock.json` along with the change.

Testing your own code                                    *chroma-nvim-tests*

The modules under `lua/chroma-vault/`, `lua/chroma-terraform/` and `lua/chroma-aws/` have a
test suite, because they handle secrets and run infrastructure commands and
being wrong there is expensive. Run it with: >

    nvim --headless --noplugin -u tests/minimal_init.lua \
         -c "lua MiniTest.run()" -c "qa!"
<
It loads mini.test and this repository's `lua/` directory — not the
configuration — so it runs in under a second and a failure cannot be somebody
else's plugin.

Two files, two purposes.

`tests/test_safety.lua` covers pure logic: parsing another tool's output,
recognising an encrypted block, detecting that credentials changed between
planning and applying, detecting credentials that override the selected
profile. There is no value in testing that conform formats Lua.

`tests/test_vault_roundtrip.lua` drives the real `ansible-vault` CLI, and
exists because of what an audit found: every defect in these modules was in an
integration path, and the unit tests would not have caught a single one. Each
case reproduces one of them — a write hook that was never attached, an option
that disabled nothing, a rename that ate a symlink, two editors clobbering each
other. It skips when ansible is not installed.

20. TROUBLESHOOTING                                *chroma-nvim-troubleshooting*

A language server is not attaching ~
>
    :checkhealth vim.lsp
<
Check "Enabled Configurations" and "Active Clients". If the server is enabled
but not attached, the filetype is usually the reason — confirm with
`:set filetype?`. If it is not enabled, check `:Mason` for whether it is
installed.

Syntax highlighting is missing for a filetype ~

The parser is probably absent: >

    :TSInstall <language>
<
`terraform` and `hcl` are built from the same upstream archive and can collide
when the whole parser set installs at once. If either is missing after a fresh
install, `:TSInstall terraform hcl` fixes it.

Completion is poor or missing ~

Confirm the server attached at all (above). If it did, check that blink loaded
before it: `:Lazy` should show blink.cmp as loaded at startup, not lazily.

Something external is missing ~
>
    :checkhealth chroma
<
Reports which of the external programs this config depends on are present,
and what stops working without each one. Most "feature X does nothing"
reports resolve here — a missing `terraform`, `bat` or kubeconfig produces
silence rather than an error.

A key does nothing ~

If it is a control key, suspect Zellij first — see |chroma-nvim-zellij|. Lock
Zellij with Ctrl-g and try again; if the key then works, Zellij was eating it.

Plugins are in a strange state ~
>
    :Lazy restore     return every plugin to the committed lockfile
    :Lazy sync        install, clean and update to match the specs
<

21. COMPONENTS                                         *chroma-nvim-components*

Chroma is not all-or-nothing. Everything past the editor itself belongs to a
component, and a component can be switched off — its language servers, Mason
packages, linters, treesitter parsers, formatters, schema mappings, plugins and
modules all go with it.

There are nine:

  core                Always on, never a choice. The editor: plugin
                      management, treesitter, pickers, YAML and Lua support.
  terraform           Terraform and OpenTofu: plan and apply from the editor,
                      `terraform fmt` on save, terragrunt.
  kubernetes          Cluster views, contexts, namespaces, and the schema
                      mapped onto manifest paths.
  helm                Charts: filetype detection, helm_ls, rendering. It does
                      not require kubernetes — `helm template` and `helm lint`
                      work with no cluster at all.
  ansible             Playbooks and roles, and the language server.
  vault               Ansible Vault files, edited in place. It does not
                      require ansible: nothing here needs playbooks.
  aws                 Profile and region for the session, and Terraform plans
                      bound to an identity.
  docker              Dockerfiles and compose files.
  github-actions      Workflow linting.

Every one of them requires core, and nothing else requires anything else.

Where the selection lives ~

                                                  *chroma-nvim-components-file*
>
    $XDG_CONFIG_HOME/chroma/components.json
<
It belongs to you, not to the release: an update replaces the configuration
tree wholesale, and what you chose has to survive that. The file is written by
`chroma install` and `chroma components`, which validate a selection against the
contract of the release that is installed. Writing it by hand is supported and
read the same way.
>
    {
      "schema": 1,
      "selected": ["terraform", "aws"]
    }
<
`core` is not listed. It is always enabled, so naming it is an error rather
than something quietly ignored — a file that lists it was written against a
different idea of what this document means. Dependencies are not listed either:
they are worked out when the file is read, so a component whose requirements
change is never described by a stale copy of them.

Three answers, not two ~

                                                 *chroma-nvim-components-modes*
The file being absent is not the same as it being empty, and neither is the
same as it being broken:
>
    no file            legacy     every component runs
    valid file         selected   the selection runs, dependencies included
    "selected": []     selected   core alone
    unreadable file    safe       core alone, with an error on startup
    broken components/ safe       core alone, with an error on startup
<
The first line is a promise to anyone who has been using this before components
existed: nothing is switched off by an update. The last is the opposite case —
the file is there, so a choice was made, and a choice that cannot be read is
still a choice. Running everything would override it in the one direction that
cannot be taken back, since `"selected": []` is a deliberate core-only.

Safe mode says what is wrong with the file and leaves the editor working well
enough to fix it. Fix the file, or delete it to go back to running everything.

It has a second cause, and it is worth telling them apart before editing
anything. A component file in the configuration tree that cannot be read also
drops Chroma into safe mode, even when the selection is perfectly good: the
contract is what says which component requires what, so half of it is not
something to resolve a selection against. `:checkhealth chroma` names which of
the two happened; a startup message names the file.

What is running now ~

`:checkhealth chroma` reports the mode, the components enabled, and — for each
component — whether the tools it needs are on PATH. It reads the files fresh,
so it can be run straight after editing a selection.

The contract ~

                                              *chroma-nvim-components-contract*
`components/*.json` in the configuration tree is the definition of each
component: what it requires, which tools it needs and what it contributes to
the editor. It is read by this configuration and by the CLI, and neither owns
it. A component file is refused rather than half-read — an unknown field, a
version that says two things, a list that is not a list — because a contract
that decides what gets installed cannot have a typo that means "install less
than asked".

`cli/DESIGN.md` in the repository documents the format and the reasoning.

22. RULES                                                   *chroma-nvim-rules*

Two rules govern this repository. `CONTRACT.md`, in this directory and so in
this installation, is the full version.

Rule #1 — zero code from memory ~

For every plugin, in order: read the current documentation, check for breaking
changes, and only then write configuration. This project exists because
configurations written from memory kept landing on APIs that no longer
existed. Everything in this configuration that surprised us — the deprecated
lspconfig pattern, the treesitter branch split, mason-lspconfig dropping
`setup_handlers`, Neovim shipping its own `catppuccin` colorscheme — would have
been written wrong from memory.

Both rules, and the reasoning behind every other choice in this configuration,
are written up in `DECISIONS.md`, beside this file — including what is
deliberately absent and why. Read that before changing something that looks
odd; most odd-looking things here are load-bearing.

Rule #2 — survey before building ~

Before writing a custom plugin, look at what already exists and judge it on
activity, licence, documentation and fit. A worse plugin somebody else
maintains beats a better one only we maintain, unless the gap is real.
